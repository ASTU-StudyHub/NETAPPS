# Лабораторная работа №5 — Сниффер пакетов

Программа перехватывает пакеты на сетевом интерфейсе `en0` (обычно Wi-Fi на Mac) и после каждого чтения печатает число полученных байт и первые 64 байта в шестнадцатеричном виде; заголовки пакетов не разбираются. Пакеты берутся из BPF (Berkeley Packet Filter) — устройства ядра macOS `/dev/bpfN`, которое отдаёт копии пакетов интерфейса. Файл: `Sniffer.java` — программа.

## Запуск

Нужна Java 25 или новее. Из папки `lab5`:

```bash
sudo "$(which java)" --enable-native-access=ALL-UNNAMED Sniffer.java
```

- `"$(which java)"` — полный путь к той же Java, что запускается без `sudo`. У `sudo` может быть свой `PATH`, и тогда найдётся `/usr/bin/java` — заглушка Apple, которая отвечает `Unable to locate a Java Runtime`.
- `--enable-native-access=ALL-UNNAMED` разрешает вызов функций C. Без флага программа тоже работает, но сначала печатает четыре строки `WARNING: A restricted method in java.lang.foreign.Linker has been called …`.
- Остановка — Ctrl+C. Другой интерфейс задаётся строкой `String iface = "en0";` (список интерфейсов — команда `ifconfig`).

## Как это работает

- В Java нет `ioctl` и доступа к устройствам, поэтому функции `open`, `ioctl` и `read` библиотеки C вызываются через Foreign Function & Memory API (`java.lang.foreign`, в стандартной библиотеке с Java 22). `linker.defaultLookup()` даёт функции libc, `libc.find("open")` находит нужную, `downcallHandle` по описанию её типов создаёт `MethodHandle`, который вызывается через `invoke`. Память для C — `MemorySegment` из `Arena.ofAuto()`, её освобождает сборщик мусора.
- Цикл вызывает `open` для `/dev/bpf0`, `/dev/bpf1`, … с флагом `0` (`O_RDONLY`, только чтение). Устройство одновременно держит один процесс; занятое или недоступное отвечает `-1`, и цикл пробует следующее, всего не больше 256.
- Три вызова `ioctl` настраивают устройство:
  - `BIOCSETIF` — привязка к интерфейсу. Аргумент — `struct ifreq` из 32 байт с именем интерфейса в начале: `arena.allocate(32)` даёт нули, `ifreq.setString(0, iface)` записывает `en0`.
  - `BIOCIMMEDIATE` со значением 1 (`arena.allocateFrom(JAVA_INT, 1)`) — пакет отдаётся сразу, без ожидания заполнения буфера.
  - `BIOCGBLEN` — ядро записывает в `size` размер своего буфера: `read` на BPF принимает буфер только ровно такого размера, поэтому `buffer` выделяется размером `size.get(JAVA_INT, 0)`.
- `read` ждёт пакеты и возвращает число прочитанных байт. В одном чтении может быть несколько пакетов, перед каждым ядро ставит заголовок `bpf_hdr` (время, длины, 18 байт). Программа его не разбирает: печатает длину прочитанного и первые `Math.min(n, 64)` байт через `HexFormat`.

## Особенности реализации

- **Только macOS.** BPF — устройство ядра macOS; на Linux то же делается сокетом `AF_PACKET`, на Windows — сырым сокетом с `ioctl(SIO_RCVALL)`.
- **Права root.** Сниффер видит трафик всех программ компьютера, поэтому устройства `/dev/bpf*` доступны только root (`crw------- root`).
- **Без `Socket`.** `Socket` и `DatagramSocket` отдают только данные своего TCP-соединения или UDP-порта, без заголовков. Сырых сокетов в Java нет, а сырой сокет macOS не получает пакеты TCP и UDP, поэтому весь трафик интерфейса даёт только BPF.
- **Типы функций C описываются вручную.** `Linker` — мост от Java к функциям C. Узнать типы функции C Java не может, их задаёт `FunctionDescriptor.of(результат, аргументы…)`, где `JAVA_INT` — `int`, `JAVA_LONG` — `long`, `ADDRESS` — указатель. Ошибку в описании компилятор не обнаружит: программа получит мусор или упадёт.
- **Переменное число аргументов.** У `open` и `ioctl` в C переменное число аргументов: `int ioctl(int, unsigned long, ...)`. На Mac с процессором Apple такие аргументы передаются через стек, а не через регистры, и `Linker.Option.firstVariadicArg(2)` сообщает Java, что они начинаются с аргумента номер 2 (счёт с нуля). Без опции `ioctl` получает вместо указателя мусор со стека: похожие вызовы `ioctl` без неё возвращали `-1` или роняли JVM. У `open` третий аргумент (права нового файла) не передаётся, опция лишь повторяет объявление из C.
- **Коды `ioctl`.** `0x8020426CL`, `0x80044270L`, `0x40044266L` — значения макросов `BIOCSETIF`, `BIOCIMMEDIATE`, `BIOCGBLEN` из `<net/bpf.h>`, напечатанные программой на C. В `0x8020426C`: `0x80…` — данные идут в ядро (у `BIOCGBLEN` `0x40…` — из ядра), `0x20` = 32 байта (`struct ifreq`), `0x42` — буква `'B'`, `0x6C` — команда 108. Суффикс `L` делает литерал `long`: без него это отрицательный `int`, который Java расширяет до `0xFFFFFFFF8020426C`, и `ioctl` отвечает `-1`.
- **Адреса в выводе.** Первые 18 байт (36 hex-символов) — `bpf_hdr`, дальше Ethernet: 6 байт MAC получателя, 6 байт MAC отправителя и тип (`0800` — IPv4). Затем IP-заголовок: после его первых 12 байт идут адреса отправителя и получателя по 4 байта, например `c0a8010c` = 192.168.1.12.

## Результаты

- Значения `BIOCSETIF`, `BIOCIMMEDIATE`, `BIOCGBLEN`, напечатанные программой на C с `<net/bpf.h>` (macOS, arm64), совпадают с константами в `Sniffer.java`; там же `sizeof(struct ifreq)` = 32 и `O_RDONLY` = 0. Размер буфера BPF по умолчанию на компьютере автора — 4096 байт (`sysctl debug.bpf_bufsize`).
- Литерал без суффикса: `long a = 0x8020426C` даёт `FFFFFFFF8020426C`, с суффиксом `L` — `8020426C`.
- Без `sudo` программа сразу печатает `Не удалось открыть /dev/bpf — запустите через sudo`: все `/dev/bpf*` имеют права `crw------- root`. Без флага `--enable-native-access=ALL-UNNAMED` перед этим выводятся четыре строки `WARNING: …`, с флагом — ни одной.
- Первая строка примера: `3469d16a c1000800` — время, `7f000000 7f000000` — длина пакета 127 байт, `1200` — длина `bpf_hdr` 18 байт, всего 18 + 127 = 145 байт. Длина IP-пакета `0071` = 113 = 127 − 14 (заголовок Ethernet), тип `0800` — IPv4, протокол `06` — TCP, отправитель `c0a8010c` = 192.168.1.12 (компьютер автора), получатель `5db8d822` = 93.184.216.34, порт назначения `01bb` = 443 (HTTPS).
- Вторая строка: 72 = 18 + 54 (`36000000`). В строках «260 байт» и «3048 байт» первый пакет чтения имеет длину `0x42` = 66 и `0x5e2` = 1506 байт; это ответы с порта 443 на 192.168.1.12, MAC-адреса и IP-адреса в них стоят в обратном порядке.
